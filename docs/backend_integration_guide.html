01

파일 반입

2개가 한 세트다. career_analysis_comprehensive.py 가 hallucination_guard.py 하나만 import 한다 — 상대 경로가 아니라 같은 디렉터리 안의 평범한 모듈 import이므로 폴더를 나누면 그 자리에서 ImportError. 

career_analysis_comprehensive.py   # 출력 — 진입점, main()
        │
        └─ import hallucination_guard    (점검 — 환각 가드 + STAR 품질 채점, 함수 14개)
career_analysis_comprehensive.py출력. 크롤러 · 프롬프트 빌더 · 검증 오케스트레이션 · 응답 envelope 모델(구 analysis_response.py) · main(). 약 1,980행
hallucination_guard.py점검. URL 프로브 · 그라운딩 대조 · 자격증 레지스트리 · STAR 근거 검증 · STAR 품질 채점 10개 루브릭(구 star_quality.py). 약 1,300행. LLM을 직접 호출하지 않음

왜 2개뿐인가

파일을 여러 개로 쪼개 둘수록 노트북 환경에서 "이 셀은 이 파일까지만"의 경계를 사람이 손으로 지켜야 한다. 그 경계를 잘못 그으면 ModuleNotFoundError(파일이 아예 안 만들어짐) 또는 SyntaxError(다음 파일의 %%writefile 줄이 이전 파일 안에 텍스트로 섞여 들어감)로 이어진다. "점검 하나, 출력 하나"로 묶어 그 실수 표면 자체를 줄였다.

tests/, docs/, cover_letter_ai_all_in_one.py(다른 기능)는 실행에 불필요하니 넘기지 않아도 된다.

04

런타임 요구사항

항목내용
실행 모델동기·블로킹. asyncio 이벤트 루프 안에서 직접 호출하면 그 스레드가 전체 요청 동안(수십 초~) 막힌다. FastAPI 등 비동기 서버라면 run_in_executor / 별도 워커 프로세스로 돌릴 것
네트워크Gemini API(고정 호스트) + 임의의 외부 호스트 — URL 크롤링(deep_crawl_site)과 링크 실재 검증(probe_url)이 사용자가 준 도메인·검증 후보 URL로 직접 아웃바운드 HTTP 요청을 보낸다. 아웃바운드가 화이트리스트로 막힌 환경이면 이 두 경로가 전부 실패로 처리된다(안전하게 실패 — 크래시 아님)
동시성_client 가 모듈 전역 싱글턴(지연 초기화). 멀티스레드 워커에서 최초 호출이 동시에 여러 번 겹치면 초기화 경합 가능성이 있다 — 멀티프로세스 워커(각 프로세스가 독립된 _client)를 쓰거나, 앱 시작 시 get_client() 를 한 번 미리 불러 워밍업할 것
LLM 호출 횟수요청 1건당 최소 2회, 최대 약 9회. 임베딩 1 + 본 분석 1 + (자격증/동아리/공모전 각 카테고리에 검증 대상이 있을 때만 반증 이중 검증 2회씩, 최대 6) + 채용공고 검색 1
HTTP 프로브검증 통과 후보당 URL 접속 확인 1회 이상. 실행당 상한 _MAX_URL_PROBES = 40, 개별 타임아웃 10초
소요 시간실측하지 않았다. LLM 호출 수·크롤링 페이지 수·URL 프로브 수가 요청마다 달라 정확한 범위를 제시할 수 없다. 방금 열거한 호출 수 상한으로 대략적인 감을 잡되, 타임아웃 예산은 넉넉히(수 분 단위) 잡을 것을 권장한다

05

호출 방식

권장

같은 Python 프로세스 안에서 main() 을 함수로 직접 호출하고, 반환된 객체를 그대로 쓴다. stdout 을 파싱할 필요가 전혀 없다.

from career_analysis_comprehensive import main

resp = main(
    user_input=["사용자가 적은 경력/활동 텍스트..."],  # list[str]
    school="서울대학교",       # 선택, 없으면 ""
    department="경영학과",     # 선택, 없으면 ""
)

resp.status          # "success" | "error"
resp.result           # dict — status=="success" 일 때 채워짐
resp.vector            # list[float] | None — 3072차원 임베딩
resp.message           # status=="error" 일 때만

# API 응답으로 그대로 내보낼 거면:
resp.model_dump_json(exclude_none=True)

user_input 은 list[str] 이다 — 한 줄짜리 URL 하나만 담긴 리스트면 그 URL을 크롤링하고(Notion URL은 전용 크롤러), 한 줄짜리이면서 로컬 파일 경로로 존재하면 그 파일을(txt/pdf) 읽는다. 그 외에는 리스트를 줄바꿈으로 합친 텍스트 그대로를 분석 대상으로 쓴다 — 이 자동 분기는 get_user_input() 안에 있다.

CLI/서브프로세스로 띄워야 한다면

__main__ 블록이 stdin을 읽어 실행하는 경로도 있다.

export GEMINI_API_KEY="..."
export USER_SCHOOL="서울대학교"
cat career_text.txt | python3 career_analysis_comprehensive.py

이 경로를 쓸 경우 §7 로 반드시 넘어갈 것 — stdout에 진행 로그와 최종 JSON이 섞여 나온다. 서브프로세스의 stdout을 그대로 json.loads() 하면 파싱이 깨진다.

06

입출력 계약

resp 는 career_analysis_comprehensive.py 에 정의된 pydantic BaseModel 이다(구 analysis_response.py 의 내용이 여기로 흡수됨). 응답 모델은 pydantic 으로 통일하는 것이 규칙이며, 미설치 환경을 대비한 대체 구현은 두지 않는다 — requirements.txt 의 pydantic>=2.0 은 선택이 아니라 필수다.

성공
{
  "status": "success",
  "vector": [0.0123, -0.0456, ...],  // 3072차원, 임베딩 실패 시 생략(exclude_none)
  "result": {
    "brief_summary": "...", "detailed_summary": "...",
    "additional_recommendations": { "certifications": [...], "clubs_and_societies": [...], "projects_and_contests": [...] },
    "resume_star_format": [...],
    "star_analysis_status": { "generated": true, "quality_review": {...} },
    "strength_diagnosis": {...}, "critical_diagnosis": {...},
    "verified_jobs": [...],
    "recommendation_notices": [...],
    "verification_audit": { "summary": {...}, "records": [...] },
    "rejected_by_guard": {...},
    "guard_version": "v3.1"
    // … 총 130개 필드. 전체 스키마는 comprehensive_field_spec_v3.1.html 참조
  }
}
실패
{ "status": "error", "message": "사람이 읽을 수 있는 실패 사유" }

result 안에는 status 와 vector 가 들어가지 않는다 — main() 마지막에 {k:v for k,v in result.items() if k not in ("status","vector")} 로 명시적으로 제거한다. 백엔드가 result 를 그대로 DB에 저장하거나 프론트로 넘겨도 이 두 키가 중복으로 섞여 들어올 일은 없다.

전체 필드 명세

result 안의 130개 필드를 하나하나(타입·필수여부·시스템/모델 출처)까지 문서화한 레퍼런스가 별도로 있다 — docs/comprehensive_field_spec_v3.1.html. DB 스키마나 직렬화 모델을 만들 때는 그 문서를 기준으로 삼을 것.

07

stdout / stderr 함정

가장 흔히 터지는 연동 버그

main() 은 진행 상황을 88곳에서 평범한 print() 로 stdout에 씁니다. 최종 결과 JSON도 print(resp.model_dump_json(...)) 로 같은 stdout에 찍힙니다. stderr로 명시적으로 보내는 로그는 강점·약점·감사 요약 3종(_log_*_summary) 총 10곳뿐입니다.

즉 서브프로세스를 띄워 stdout 전체를 캡처해 json.loads() 하면 아래처럼 진행 로그 뒤에 JSON이 붙은 텍스트를 받게 되고, 파싱이 그 자리에서 깨집니다. 

=================================================================
  Career Analysis AI - COMPREHENSIVE Edition v3.1
  모델: gemini-2.5-pro  |  임베딩: gemini-embedding-001
  ...
[1] 입력 데이터 STAR 적합성 사전 판정...
  경험 블록 3개 중 STAR 기준 충족 2개 → 생성 진행
...
{
  "status": "success",
  ...
}

해결책 우선순위

  1. 가장 확실함 — §5의 권장대로 같은 프로세스에서 함수로 직접 호출하고 반환값을 쓴다. stdout을 볼 필요 자체가 없다.
  2. 어쩔 수 없이 서브프로세스여야 한다면, stdout에서 마지막 줄부터 거슬러 올라가며 최상위 { 로 시작하는 지점을 찾아 그 뒤부터만 파싱한다(clean_json_response() 가 내부적으로 하는 것과 같은 방식 — 중괄호 깊이를 세어 최상위 JSON 블록만 추출).
  3. 또는 main() 호출부의 print() 들을 로깅 모듈로 바꿔치기하는 몽키패치를 백엔드 쪽에서 감싸 적용한다(코드 수정 없이 builtins.print 를 컨텍스트 매니저로 리다이렉트).

아래 표는 전부 이 환경에서 실제로 재현해 확인한 값이다(추정 아님).

상황statusmessage (실측)
입력 10자 미만error"입력 데이터가 너무 짧습니다. 최소 10자 이상 입력하세요."

크롤링 실패(URL 접속 불가 등)success 유지크래시하지 않음. "크롤링 실패" 안내문을 원문으로 대체해 분석에 넘기고, 모델에게 추론 금지를 명시
동아리/자격증/공모전 검증 통과 0건success 유지빈 배열 반환. recommendation_notices 에 사유 문장 추가 (정상 결과로 취급)

09

재시도 · 타임아웃

대상설정값동작
LLM 호출 재시도최대 4회레이트리밋(429/quota/resource_exhausted)에만 재시도. 지수 백오프 5s → 10s → 20s → (4번째는 대기 없이 마지막 시도, 실패 시 예외 전파). 단일 요청이 최악의 경우 백오프만으로 35초 이상 지연될 수 있다
웹 크롤링 fetch15초페이지·PDF 요청당. 최대 30페이지 + 5개 PDF까지 순회
URL 실재성 프로브10초검증 통과 후보 URL 접속 확인당. 실행당 상한 40회
레이트리밋이 아닌 예외재시도 없음즉시 상위로 전파 → 해당 호출을 감싼 _call_model/_call_model_grounded 가 캐치해 빈 결과 또는 에러로 처리

4

실제 키로 종단 1회 실행

짧은 텍스트 하나로 실제 Gemini 호출까지 태워 resp.status == "success" 와 result 안에 §6의 필드들이 채워지는지 확인한다. 이 단계는 이 안내서를 작성하는 동안 수행하지 않았다 (§11 참조) — 백엔드 쪽에서 최초 1회는 반드시 직접 확인할 것을 권장한다.

11

알려진 한계

실제 API로 종단 실행된 적이 없다

이 저장소의 환각 가드·품질 채점 로직은 43건의 단위 테스트로 검증됐고, 그라운딩 응답 필드명(grounding_chunks, web_search_queries 등)은 google-genai 2.14.0 소스와 직접 대조했다. 그러나 main() 을 실제 GEMINI_API_KEY 로 처음부터 끝까지 실행해 본 적은 없다. §10-4 를 백엔드 쪽에서 반드시 수행할 것.

  • 비용 미측정 — 요청 1건당 LLM 호출 2~9회, 이 중 검색 그라운딩이 걸린 호출은 일반 호출보다 비용이 높다. 실사용 트래픽으로 비용을 먼저 추정해 볼 것.
  • 동시 요청 처리량 미측정 — 워커 수·큐잉 전략은 §4의 블로킹·싱글턴 특성을 감안해 백엔드 쪽에서 설계해야 한다.
  • 레이트리밋 임계값 실측 없음 — 4회 재시도·지수 백오프가 실제 Gemini 쿼터 하에서 충분한지는 트래픽을 걸어봐야 안다.
  • 인용↔본문 함의 미검사 — STAR 슬롯의 *_source_quote 가 원문에 실제로 존재하는지는 검사하지만, 본문 서술이 그 인용문에서 논리적으로 도출되는지는 검사하지 않는다.
