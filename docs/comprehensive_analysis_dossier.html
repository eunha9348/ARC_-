01

시스템 개요

사용자의 경력·활동 기록을 받아 역량 분석 · 강점/약점 진단 · STAR 이력서 초안 · 추가 활동 추천을 생성하는 모듈이다. 입력은 직접 텍스트, 파일 경로(텍스트/PDF), 또는 URL(Notion 포함)이며, 출력은 단일 JSON envelope 다.

INPUT

세 가지 입력 경로

직접 텍스트 · 파일(txt/pdf) · URL. URL 은 Notion 전용 크롤러와 일반 딥 크롤러로 분기한다.

ANALYSIS

단일 LLM 호출

Gemini 2.5 Pro 로 요약·클러스터링·시너지·강점·약점·STAR 를 한 번에 생성한다. 이 호출에는 검색을 붙이지 않는다.

VERIFY

후보 검증 단계

추천 항목은 '최종 추천'이 아니라 '검증 후보'로 생성되고, 별도 관문을 통과한 것만 살아남는다.

OUTPUT

감사 추적 동반

무엇이 왜 제거되었는지 verification_audit 으로 함께 나간다.

산출물 구성

  • 요약·클러스터링 — 한 줄 요약, 심층 요약, 성향/역량/직군 키워드
  • 시너지 조합 — 보유 항목 간 결합 효과 2~5개
  • 강점 진단 — 7개 카테고리, level 3단계, 근거 인용 필수
  • 보완점 진단 — 7개 카테고리, severity 3단계, 완화 표현 금지
  • STAR 이력서 초안 — 근거 결속 + 품질 등급 (§6)
  • 추가 추천 — 자격증 / 동아리·학회 / 공모전 (전부 검증 통과분만)
  • 채용공고 — 검색 그라운딩 단계에서만 생성
  • 액션 플랜 — 단기/중기/장기

02

신뢰 모델

제1 원칙

모델의 자기 보고는 신뢰 원천이 아니다. 모델이 "verified": true 라고 말하는 것은 그 자체로 아무 효력이 없다. 환각을 막는 모든 판정은 결정론적 코드가 내리고, 프롬프트는 보조 수단으로만 쓴다.

시스템이 인정하는 신뢰 원천은 셋뿐이다.

원천무엇을 보증하는가어디에 쓰이는가
1 사용자 입력 원문 사용자가 실제로 적은 사실 STAR 전 슬롯, 강점·약점 근거, 모든 수치
2 검색 그라운딩 모델 주장이 아닌 실제 검색 결과 chunk 자격증·동아리·공모전 실재성, 채용공고 생성
3 실제 HTTP 응답 링크가 지금 살아 있고 그 내용이 맞다는 사실 모든 URL 부착

이 셋 중 어느 것으로도 뒷받침되지 않는 값은 코드가 기계적으로 제거한다. 제거는 조용히 일어나지 않고 전부 감사 로그에 남는다.

03

파이프라인 전체 로직

main() 은 8단계로 구성된다. 각 단계는 앞 단계의 실패를 삼키지 않고 fail-closed 로 전파한다.

0

입력 수집

단일 URL 이면 크롤링, 파일 경로면 읽기, 그 외에는 텍스트로 취급한다. Notion URL 은 __NEXT_DATA__ 블록 파싱 → OG 메타 → HTML 텍스트 순으로 시도한다. 일반 URL 은 같은 오리진을 BFS 로 훑고 PDF 를 우선 큐잉한다.

크롤링에 실패하면 추론하지 않는다. v2.0 은 URL 슬러그로 내용을 "최대한 추론"하라고 지시했는데, 그것이 환각 생성 지시였다. v3 는 데이터 부재를 그대로 하류에 알린다.

IN lines[] OUT raw_content GUARD 추론 금지 지시문
1

STAR 적합성 사전 판정 — LLM 호출 전

입력을 경험 블록으로 쪼개고 5개 신호(분량·행동동사·수치성과·기간·역할)로 채점한다. 4개 이상을 만족하는 블록이 하나도 없으면 STAR 생성을 아예 요청하지 않고 스키마에서 필드를 제거한다.

"부족하면 만들지 말라"를 LLM 판단에 맡기지 않는 것이 핵심이다. '부족'의 정의를 코드가 갖는다.

IN raw_content OUT StarReadiness GUARD assess_star_readiness()
2

임베딩 생성

gemini-embedding-001 로 벡터화한다. SDK 시그니처 차이를 대비해 3가지 호출 형태를 순차 시도하고, 전부 실패해도 분석은 계속한다 (벡터는 검색용 부가 산출물이므로 분석을 막지 않는다).

IN raw_content[:10000] OUT vector | None
3

본 분석 — 검색 없는 단일 호출

요약·클러스터링·시너지·강점·약점·(조건부)STAR 를 생성한다. 추천 항목은 최종 추천이 아니라 검증 후보로 생성되며, verification_query 를 함께 요구한다.

프롬프트 스키마에는 url 필드가 존재하지 않는다 — 모델이 URL 을 출력할 자리 자체를 없앴다. 그럼에도 URL 이 섞여 들어오는 경우를 대비해 호출 직후 scrub_model_urls() 로 1차 스크럽한다.

IN raw_content, school, dept, star_ready OUT result dict GUARD scrub_model_urls()
4

추천 후보 검증

자격증 → 동아리 → 공모전 순으로 각각 독립 검증한다. 공통 구조는 반증형 이중 검증이다: "존재를 확인하라"가 아니라 "실재하지 않는다는 증거를 찾아라"로 프롬프트를 뒤집고, 온도가 다른 2회 호출(0.0 / 0.4)이 모두 통과해야 인정한다.

추천 이유 같은 생성 맥락은 검증 프롬프트에 넘기지 않는다 — 확증편향 차단. 자격증은 검색 전에 레지스트리·등급 문법으로 먼저 거른다(§5).

개수 쿼터는 없다. 0개도 정상 결과이며, 빈 결과에는 사유와 사용자가 직접 확인할 검색어가 붙는다.

IN 후보 리스트 OUT 통과분 + rejected_by_guard GUARD 그라운딩 대조 · URL 프로브
5

STAR 근거 검증 + 품질 채점

두 관문을 순서대로 통과시킨다. 먼저 validate_star_entries() 가 근거를 검사하고(위반 시 폐기), 살아남은 항목만 evaluate_star_entries() 가 품질을 채점한다 (미달이어도 폐기하지 않고 등급·개선 지시를 부착).

IN resume_star_format, raw_content OUT 검증분 + quality + star_analysis_status GUARD 인용 대조 · 수치 검사 · 중복도
6

채용공고 — 검색 그라운딩 단계

본 분석에서 만들지 않는다. 직무 키워드로 그라운딩 검색을 돌려 검색 결과에서만 공고를 만들고, 회사명이 검색 근거에 등장하는지 대조한 뒤, 근거 URI 를 HTTP 프로브해 통과한 것만 남긴다.

채용공고는 링크 없이는 실행 불가능한 추천이므로, URL 검증 실패 시 항목 자체를 제외한다(동아리는 링크 없이도 유지).

IN target_job_keywords OUT verified_jobs GUARD 그라운딩 + probe_url()
7

최종 스크럽 · 감사 · 직렬화

검증을 통과한 URL 집합을 allowlist 로 삼아 결과 전체를 다시 훑고 (2차 스크럽), 감사 로그와 제거 목록을 붙인 뒤 envelope 로 직렬화한다. stdout 은 JSON 전용이고 요약 로그는 stderr 로 분리한다.

OUT VectorSuccessResponse{ status, result, vector } GUARD scrub_model_urls(allowlist)

04 — 필드 리포트

장애 기록: v2.0 환각 사고

보고된 증상

H-1

접속되지 않는 동아리·학회 링크

추천 카드의 URL 이 404 이거나, 200 을 반환하지만 실제로는 존재하지 않는 페이지였다.

H-2

재구조화에 불과한 STAR

네 칸이 사용자가 쓴 한 문장을 표현만 바꿔 나눠 담았다. 입력이 빈약할 때는 없는 상황과 성과 수치를 지어냈다.

H-3

존재하지 않는 자격증

완전 허구보다 실재 자격증 + 없는 등급 조합이 더 많았고 더 오래 살아남았다.

핵심 진단

v2.0 의 환각 방지 규칙 9개는 잘 쓰인 규칙이었다. 문제는 그것이 전부 모델에게 하는 부탁이었고, 같은 파일 안에서 코드가 강제한 것은 정반대였다는 점이다 — 개수를 채우라는 쿼터, 채울 자리가 있는 스키마, 모델의 자기 보고를 그대로 믿는 검증기.

규칙은 요청이고 구조는 강제다. 둘이 충돌하면 항상 구조가 이긴다.

구조적 원인 13건

C-1

쿼터가 "확실하지 않으면 제외"를 무력화

규칙 3("최소 3개")과 규칙 1·4("확실하지 않으면 제외")가 정면 충돌한다. 확실한 항목이 1개뿐일 때 둘을 동시에 만족시킬 방법은 없고, 정량 목표가 정성 목표를 이긴다. 게다가 이 쿼터는 코드에도 있었다 — 검증 탈락으로 개수가 모자라면 더 지어내라고 다시 요청했다. 

"실재 여부가 확실하지 않으면 제외하되,
 제외로 인해 3개 미만이 되면 ... 보충하여 3개를 채울 것"

if len(result) < min_clubs and school:
    extra_raw = _request_broader_clubs(school, department, existing_names)
C-2

생성자와 검증자가 같은 모델·같은 기억

항목을 만든 바로 그 gemini-2.5-pro 에게 "verified": true/false 를 물었다. 같은 파라메트릭 메모리를 공유하는 두 호출은 독립 검증이 아니라 확증편향 증폭기다. 추천 이유까지 함께 넘겨 맥락을 주었다.

C-3

검색 도구를 붙였을 뿐, 검색했는지는 확인하지 않음

가장 큰 착시. use_google_search=True 는 도구를 사용할 수 있게 할 뿐 사용을 보장하지 않는다. 모델은 검색 없이 기억으로 답하고 거기에 verified: true 를 붙일 수 있으며, v2.0 은 grounding_metadata 를 한 번도 읽지 않았다.

C-4

동아리·공모전·자격증 URL 은 접속 확인을 거치지 않음

_verify_url_content() 는 채용공고에만 적용되었다. 나머지 세 카테고리는 모델이 말한 official_url 을 그대로 실었다. H-1 의 직접 경로다.

C-5

채용공고 URL 검사조차 soft-404 를 통과시킴

status < 400 만 확인해, 200 을 주면서 "페이지를 찾을 수 없습니다"를 보여주는 페이지가 전부 통과했다. is_job 은 페이지 어딘가에 "채용" 한 단어만 있으면 참이 되는데, 그 단어는 거의 모든 기업 사이트의 전역 내비게이션에 있다.

C-6

누락된 판정값이 '통과'로 기본 처리 (fail-open)

if not vr.get("deadline_ok", True):   # 필드 누락 → 통과
    continue
# upcoming 은 프롬프트에만 존재, 코드에서 미검사 → 끝난 공모전이 나감

except ValueError:
    valid.append(job)              # 마감일 파싱 실패 → 유효 처리
C-7

검증 결과를 원문 문자열 그대로 매칭

vmap = {r.get("name",""): r} — 검증자가 (사)한국OO협회 를 한국 OO 협회 로 되돌려주면 매칭이 실패한다. 결과가 무작위로 흔들렸고 추적할 방법도 없었다.

C-8

규칙은 "만들지 말라", 스키마에는 채울 자리가 있음

H-2 의 핵심. 규칙 7 은 데이터가 부족하면 STAR 를 만들지 말라고 했는데, 출력 스키마에는 resume_star_format 이 예시 객체와 함께 항상 있었고 "부족하다"를 담을 필드는 없었다. 모델이 스키마를 지키면서 규칙을 지킬 방법이 없으면 스키마가 이긴다.

C-9

STAR 만 근거 인용 의무에서 제외

강점·약점 진단은 항목마다 evidence 를 요구했는데 STAR 의 S·T·A·R 에는 근거 요구가 없었다. 출처를 묻지 않으면 모델은 가장 쉬운 길을 간다 — 있는 문장을 네 칸에 나눠 담거나(재구조화), 빈 칸을 지어낸다(창작). 두 증상이 한 원인에서 나왔다.

C-10

크롤링 실패 시 "추론하라"고 지시

f"[크롤링 실패]\n"
f"URL 경로명과 도메인을 바탕으로 내용을 최대한 추론하십시오.\n"

환각 방지 규칙이 아니라 환각 생성 지시문이었다.

C-11

채용공고를 검색 없이 먼저 만들고 나중에 지움

본 분석 호출은 use_google_search=False 였다. 존재하지 않는 공고를 기억으로 먼저 만들어 놓고 사후 필터에 전부를 걸었다. 생성-후-필터링은 추천 도메인에서 잘못된 순서다.

C-12

쿼터 보충 경로가 검증을 더 느슨하게 통과

보충 루프에서는 wrong_school 과 verified 만 확인하고 교차 학교 확인을 생략했다. 가장 지어낼 가능성이 높은 경로에 가장 약한 검증이 걸려 있었다.

C-13

무엇이 왜 걸러졌는지 산출물에 남지 않음

드롭 사유는 전부 print() 로만 나갔다. 최종 JSON 만 보면 추천이 왜 비었는지 알 수 없다. 측정되지 않는 환각은 개선 여부도 확인할 수 없다.

이 밖에 운영 결함으로 API 키 소스 하드코딩, import 시점 클라이언트 생성(키 없으면 모듈 로딩 실패), main() 인자 불일치로 인한 TypeError, tool-call 파트 혼입 시 resp.text 예외 미처리가 함께 발견되어 정리했다.

06

STAR 파이프라인과 품질 채점

STAR 는 네 관문을 통과한다. 앞의 둘은 환각을, 뒤의 둘은 품질을 다룬다.

관문시점판정실패 시
① 적합성 사전 판정LLM 호출 전경험 블록 5신호 중 4개 이상생성 요청 자체를 하지 않음 + 코칭 반환
② 근거 결속생성 후인용 대조 · 수치 · 슬롯 중복슬롯 삭제 또는 항목 폐기
③ 파생 필드 검증근거 통과분headline 수치 / 회고 근거해당 필드만 삭제
④ 품질 채점마지막10개 루브릭 → A~D폐기하지 않고 등급·개선 지시 부착

왜 품질 미달을 폐기하지 않는가. 버리면 사용자는 자기 기록의 무엇이 부족한지 알 수 없다. 이 도구의 목적은 완성된 STAR 를 주는 것이 아니라 제출 가능한 STAR 를 쓸 수 있게 만드는 것이므로, 미달 항목은 등급과 함께 남기고 무엇을 어떻게 고칠지 알려준다.

전문성은 사실을 늘려서 만들지 않는다

"전문적인 STAR"를 만드는 흔한 방법은 그럴듯한 배경과 성과를 덧붙이는 것이고, 그것이 정확히 v2.0 이 실패한 방식이다. v3.1 은 반대 경로를 쓴다.

축무엇을 하는가사실을 늘리는가
선택어떤 경험을 STAR 로 쓸지 고르는 판단아니오
배분Action 이 절반을 차지하도록 분량 재배치아니오
표현"~를 했습니다"를 성취문 형태로아니오
진단부족한 요소는 지어내지 않고 채우는 법을 안내아니오

채점 루브릭 10항목

키기준근거
action_dominantAction 이 전체의 35% 이상 (권장 40~50%)Action 이 답변의 절반
context_conciseS+T 합계 45% 이하 (권장 30%)배경 과다가 가장 흔한 실패
first_personAction 에 공동 주어 없음, 또는 역할 분담 명시"가장 흔하고 가장 고치기 쉬운 실수"
action_method도구·방법·판단 기준 중 하나 이상'무엇을' 만이 아니라 '어떻게'
strong_verb성취 동사 있고 약한 서술 없음이력서 성취문 공식
result_quantifiedResult 에 수치 지표 존재수치 없는 결과는 감점
result_impact수치 외 파급 서술그 수치가 만든 변화
no_vague모호 표현이 수치 없이 쓰이지 않음"성공적" 류 무의미
slots_distinctS·T 중복도 50% 미만슬롯별 역할 분리
context_scale기간·인원·규모 중 하나 명시맥락 = 성과 크기의 척도

등급은 통과 비율로 결정된다 — A 85%↑ · B 65%↑ · C 45%↑ · D 그 미만.

실제 채점 출력

── 나열식 STAR: D (0/10)
   "사실상 경험 나열에 가깝습니다. 구조적 재작성이 필요합니다."
   ✗ Action 비중: Action 이 전체의 12% (권장 40~50%)
   ✗ 배경 간결성: Situation+Task 가 전체의 74% (권장 30% 이하)
   ✗ 개인 기여 명시: Action 에 공동 주어 1회, 개인 주체 표현 없음
   ✗ 방법 구체성: Action 에 사용한 도구·방법·접근이 드러나는지
   ✗ 성취 동사: 강한 동사 0개, 약한 서술 2개
   ✗ 결과 정량화: Result 에 수치 지표가 있는지
   ✗ 결과의 파급: 수치 외에 그 결과가 만든 변화가 서술되는지
   ✗ 모호 표현 배제: 수치 없이 모호 표현 사용: 성공적, 큰 도움
   ✗ 슬롯 역할 분리: Situation·Task 내용 중복도 80%
   ✗ 맥락 규모: 기간·인원·규모 중 하나라도 명시되는지

── 전문 수준 STAR: A (10/10)
   "제출 가능한 수준. 구조·주체·수치가 모두 갖춰져 있습니다."

요약 계층

  • headline — 이력서에 그대로 넣을 수 있는 한 줄 성취문(강한 동사 + 맥락 + 결과). S/T/A/R 에 이미 있는 사실만으로 구성하며, 원문에 없는 수치가 들어가면 자동 삭제된다.
  • competency_evidence — 이 경험이 증명하는 역량과 판단 근거. 사실이 아니라 해석이므로 창작이 아니지만 근거는 S/T/A/R 안에 있어야 한다.
  • L (회고) — 표준 STAR 에 회고 한 겹을 더한 STARR / STAR-L 형태. 원문에 배움이 명시된 경우에만 남고, 없으면 삭제된다. "무엇을 느꼈을 것이다"는 추측이므로 금지.

중복도 지표 결함과 수정

Jaccard 만으로는 짧은 슬롯이 긴 슬롯에 통째로 포함된 중복을 놓친다 — 합집합이 커져 비율이 희석되기 때문이다. Task 가 Situation 의 축약본인 경우가 정확히 이 형태이고, 이것이 "재구조화"의 전형이다. 포함도를 함께 재도록 수정했다. 

# Task 가 Situation 의 축약본인 경우
jaccard(S, T)     = 0.32   → 통과 (놓침)
containment(S, T) = 0.82   → 차단
overlap_ratio     = max(둘) → 재구조화로 판정

v2.0 대비 검증 호출이 늘었다. 카테고리(자격증·동아리·공모전)당 최대 2회 + 채용공고 1회의 그라운딩 호출이 발생하고, 여기에 URL 프로브가 더해진다. _DUAL_PASS_VERIFY = False 로 검증 호출을 절반으로 줄일 수 있으나 agreement gate 가 사라지므로 환각 통과율이 올라간다.

한계와 남은 과제

파이프라인 전체가 실제 API 로 실행된 적이 없다. 결정론적 가드는 테스트 43건으로 고정되어 있고 그라운딩 필드명은 google-genai 2.14.0 기준으로 대조 확인했으나, 통합 동작은 설계대로일 것이라는 판단이지 관측된 사실이 아니다. 실제 키로 1회 실행해 verification_audit 의 드롭 사유 분포를 확인하는 것이 가장 값어치 있는 다음 단계다.

알려진 구멍

  • 인용↔본문 함의 미검사 — 인용문이 원문에 존재하는지는 검사하지만, 본문이 그 인용문에서 실제로 도출되는지는 검사하지 않는다. 원문 문장을 정직하게 복사해 놓고 본문에 다른 이야기를 쓰면 통과한다. 수치는 막히지만 서술은 안 막힌다.
  • 재구조화는 원리상 완전 제거 불가 — 입력에 실질적인 문장이 하나뿐이면 정직한 STAR 는 반드시 그 문장의 재배치처럼 보인다. 없는 정보를 만들지 않으면서 네 칸을 채울 방법은 없다. 시스템은 이를 보이게 만들 뿐 제거하지 못한다.
  • 레지스트리는 수동 관리 목록 — 113종은 한국의 전체 자격증에 비하면 일부다. 미등재 항목은 검색 검증만으로 방어하므로, 웹 존재감이 있는 그럴듯한 가짜는 통과할 수 있다. 반대로 실재하는데 목록에 없어 탈락하기도 한다. 등급 표도 공식 등록 데이터가 아니라 지식 기반이므로 양방향 오류 가능성이 있다.
  • 수치 검사는 맨 숫자 비교 — 원문 "3년치"와 생성 "3개월"이 모두 3 이라 통과한다. 노골적 창작은 잡지만 미묘한 오귀속은 못 잡는다.
  • 이중 검증도 안정적 환각은 통과 — 온도에 걸쳐 재현되는 잘못된 믿음(그럴듯한 이름의 유명한 가짜)은 두 패스 모두 통과한다.
  • 루브릭은 표면 신호 기반 — 한국어는 주어를 자주 생략해 1인칭 판정이 어휘 표지에 의존하고, 방법 구체성은 도구명·수단 조사를 프록시로 쓴다. 문장이 실제로 얼마나 설득력 있는지는 재지 못한다. 임계값도 실사용 데이터로 조정된 값이 아니다.
  • 동아리 추천은 구조적으로 비기 쉽다 — 한국 대학 동아리는 색인된 공개 정보가 희소해 검증 통과율이 낮다. H-1 이 해소되는 방식의 일부는 그 기능이 조용해지는 것이다.

다음 단계

  1. 실제 키로 1회 실행 → verification_audit 드롭 사유 분포 확인. 어느 게이트가 일하고 어느 게이트가 과잉 차단하는지는 이 로그로만 알 수 있다.
  2. 인용→본문 함의 검사 추가 (별도 호출로 "이 인용문이 이 서술을 뒷받침하는가"만 판정)
  3. 자격증 레지스트리를 Q-Net 등 공식 등록 데이터와 동기화
  4. 학교별 공식 동아리 목록 사전 수집 — 동아리 검증의 근본 해법
  5. 루브릭 임계값을 실사용 샘플로 보정
