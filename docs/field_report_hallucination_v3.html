추천 파이프라인 환각 장애 원인 분석 및 재설계

v2.0 은 환각을 막기 위해 9개의 프롬프트 규칙을 두었지만, 존재하지 않는 링크·자격증이 그대로 사용자에게 전달되었고 STAR 분석은 입력 문장의 재배치에 머물렀다. 규칙이 부족했던 것이 아니라, 규칙과 반대 방향으로 작동하는 구조가 파이프라인 안에 있었다. 이 리포트는 그 구조를 특정하고, v3.0 에서 무엇을 바꿨는지 기록한다.

01 — 보고된 증상

무엇이 사용자에게 도달했는가

세 증상은 서로 다른 기능에서 나타났지만, 뒤에서 보듯 상당 부분 같은 뿌리를 공유한다.

H-1

접속되지 않는 동아리·학회 링크

추천 카드에 붙은 URL 이 404 이거나, 200 을 반환하지만 실제로는 존재하지 않는 페이지였다. 사용자가 링크를 눌러보기 전까지는 알 수 없었다.

H-2

재구조화에 불과한 STAR 분석

S·T·A·R 네 칸이 사용자가 쓴 한 문장을 표현만 바꿔 나눠 담았다. 반대로 입력이 빈약할 때는 없는 상황과 성과 수치를 지어냈다.

H-3

존재하지 않는 자격증 추천

완전 허구 명칭보다, 실재하는 자격증에 없는 등급을 붙인 형태 (빅데이터분석기사 2급)가 더 많았고 더 오래 살아남았다.

02 — 핵심 진단

규칙은 요청이었고, 구조는 강제였다

v2.0 의 _STRICT_HALLUCINATION_RULES 는 잘 쓰인 규칙이다. 문제는 그 규칙이 전부 모델에게 하는 부탁이었다는 점이다. 같은 파일 안에서 코드가 강제한 것은 정반대였다 — 개수를 채우라는 쿼터, 채울 자리가 있는 스키마, 그리고 모델의 자기 보고를 그대로 믿는 검증기.

모델과 코드가 충돌하면 항상 코드가 이긴다. v3.0 의 원칙은 하나다: 환각을 막는 모든 판정은 결정론적 코드가 내리고, 프롬프트는 보조 수단으로만 쓴다.

03 — 구조적 원인

코드에서 특정된 13개 결함

C-1Quota

"최소 3개" 쿼터가 "확실하지 않으면 제외"를 무력화했다

규칙 3 은 규칙 1·4 와 정면으로 충돌한다. 확실한 항목이 1개뿐일 때 모델이 규칙을 동시에 만족시킬 방법은 없고, 정량 목표가 정성 목표를 이긴다. 더 나쁜 것은 이 쿼터가 코드에도 박혀 있었다는 점이다 — 검증에서 탈락해 개수가 모자라면 _request_broader_clubs() 로 더 지어내라고 다시 요청했다. 검증 실패가 추가 환각을 유발하는 양성 피드백 루프였다.

v2.0 / 프롬프트 규칙 3 · verify_clubs_with_search 
"실재 여부가 확실하지 않으면 해당 항목은 제외하되,
 제외로 인해 3개 미만이 되면 ... 보충하여 3개를 채울 것"

if len(result) < min_clubs and school:
    extra_raw = _request_broader_clubs(school, department, existing_names)
C-2Self-verify

생성자와 검증자가 같은 모델·같은 기억이었다

verify_clubs_with_search 계열은 항목을 만든 바로 그 gemini-2.5-pro 에게 "verified": true/false 를 물었다. 같은 파라메트릭 메모리를 공유하는 두 호출은 독립 검증이 아니라 확증편향 증폭기다. 게다가 추천 이유까지 함께 넘겨 "이미 추천된 것"이라는 맥락을 검증자에게 주었다.

C-3Grounding

검색 도구를 붙였을 뿐, 검색했는지는 확인하지 않았다

가장 큰 착시였다. use_google_search=True 는 도구를 사용할 수 있게 할 뿐 사용을 보장하지 않는다. 모델은 검색 없이 기억으로 답하고 거기에 "verified": true 를 붙일 수 있으며, v2.0 은 응답의 grounding_metadata 를 한 번도 읽지 않았다. 검색 검증처럼 보였지만 실제로는 기억 기반 자기확신이었다.

C-4URL

동아리·공모전·자격증 URL 은 단 한 번도 접속 확인을 거치지 않았다

_verify_url_content() 는 채용공고에만 적용되었다. 나머지 세 카테고리는 모델이 말한 official_url 을 그대로 결과에 실었다. H-1 의 직접 경로다.

v2.0 / verify_clubs_with_search — HTTP 요청 없음 
official_url = vr.get("official_url")
club["url"] = official_url if official_url and official_url != "null" else None
C-5Soft-404

채용공고 URL 검사조차 soft-404 를 통과시켰다

status < 400 만 확인했기 때문에, 200 을 주면서 "페이지를 찾을 수 없습니다"를 보여주는 페이지가 전부 통과했다. 콘텐츠 대조도 느슨했다 — is_job 은 페이지 어딘가에 "채용" 한 단어만 있으면 참이 되는데, 그 단어는 거의 모든 기업 사이트의 전역 내비게이션에 있다.

C-6Fail-open

누락된 판정값이 '통과'로 기본 처리되었다

vr.get("deadline_ok", True) — 검증자가 필드를 빠뜨리면 마감 검사를 통과한다. upcoming 은 프롬프트로 요구했지만 코드에서 아예 읽지 않아, 이미 끝난 공모전이 그대로 나갔다. 채용 마감일 파싱 실패도 마찬가지로 유효 처리했다.

v2.0 / verify_contests_with_search · filter_valid_jobs 
if not vr.get("deadline_ok", True):   # 필드 누락 → 통과
    continue
# upcoming 은 프롬프트에만 존재, 코드에서 미검사

except ValueError:
    valid.append(job)              # 파싱 실패 → 유효 처리
C-7Mapping

검증 결과를 원문 문자열 그대로 매칭했다

vmap = {r.get("name",""): r} — 검증자가 (사)한국OO협회 를 한국 OO 협회 로 되돌려주면 매칭이 실패한다. 이 실패는 결과를 무작위로 흔들었고, 어느 방향으로 흔들렸는지 추적할 방법도 없었다.

C-8Schema

규칙 7 은 "만들지 말라"고 했지만 스키마에는 채울 자리가 있었다

H-2 의 핵심 원인이다. 규칙 7 은 데이터가 부족하면 STAR 를 만들지 말고 그 사실을 알리라고 했는데, 출력 스키마에는 resume_star_format 이 예시 객체와 함께 항상 존재했고, "부족하다"는 사실을 담을 필드는 어디에도 없었다. 모델이 스키마를 지키면서 규칙을 지킬 방법이 없으면, 스키마가 이긴다.

v2.0 / build_system_prompt_comprehensive — 조건 없이 항상 포함 
'  "resume_star_format": [\n'
'    {"title":"경험명","S":"상황","T":"과제","A":"행동","R":"결과"}\n'
'  ],\n'
# star_skipped / insufficient_data 를 담을 필드가 스키마에 없음
C-9Evidence

STAR 만 근거 인용 의무에서 빠져 있었다

strength_diagnosis 와 critical_diagnosis 는 항목마다 evidence 를 요구했다. 그런데 STAR 의 S·T·A·R 에는 아무 근거 요구가 없었다. 출처를 묻지 않으면 모델은 가장 쉬운 길을 간다 — 있는 문장을 네 칸에 나눠 담거나 (재구조화), 빈 칸을 그럴듯한 이야기로 채운다(창작). 두 증상이 한 원인에서 나왔다.

C-10Inference

크롤링에 실패하면 "추론하라"고 지시했다

Notion 크롤링이 빈약하거나 실패했을 때 v2.0 은 URL 슬러그와 도메인으로 내용을 "최대한 추론"하라고 지시했다. 이것은 환각 방지 규칙이 아니라 환각 생성 지시문이었다.

v2.0 / get_user_input — 크롤링 실패 경로 
f"[크롤링 실패]\n"
f"URL 경로명과 도메인을 바탕으로 내용을 최대한 추론하십시오.\n"
C-11Order

채용공고를 검색 없이 먼저 만들고 나중에 지웠다

본 분석 호출은 use_google_search=False 였다. 즉 존재하지 않는 공고를 기억으로 먼저 만들어 놓고, 사후 필터가 얼마나 촘촘한지에 전부를 걸었다. 생성-후-필터링은 추천 도메인에서 잘못된 순서다.

C-12Bypass

쿼터 보충 경로는 검증을 더 느슨하게 통과시켰다

개수를 채우는 보충 루프에서는 wrong_school 과 verified 만 확인하고 교차 학교 확인을 생략했다. 가장 지어낼 가능성이 높은 경로에 가장 약한 검증이 걸려 있었다.

C-13Blind

무엇이 왜 걸러졌는지 산출물에 남지 않았다

드롭 사유는 전부 print() 로만 나갔다. 최종 JSON 만 보면 추천이 왜 비었는지, 환각이 몇 건 걸러졌는지 알 수 없다. 측정되지 않는 환각은 개선 여부도 확인할 수 없다.

이 밖에 운영상 결함으로 API 키 소스 하드코딩, import 시점 클라이언트 생성(키 없으면 모듈 로딩 자체가 실패), main() 의 인자 불일치(if __name__ == "__main__" 에서 TypeError), tool-call 파트 혼입 시 resp.text 예외 미처리가 함께 발견되어 v3.0 에서 정리했다.

04 — 적용된 수정

v3.0 재설계

신뢰 원천을 셋으로 한정했다: 사용자 입력 원문, 검색 그라운딩 메타데이터, 실제 HTTP 응답. 이 셋 중 무엇으로도 뒷받침되지 않는 값은 코드가 기계적으로 제거한다.

F-1

쿼터 전면 폐지

규칙 3 과 min_clubs 보충 루프, _request_broader_clubs() 를 모두 삭제했다. 0개도 정상 결과로 취급하고, 대신 recommendation_notices 로 "확인되지 않은 항목을 채워 넣지 않았다"는 사실과 사용자가 직접 확인할 검색어를 제공한다.

해소: C-1 · C-12 — H-1 의 1차 원인

F-2

URL 무생성 원칙 (Zero-Trust URL)

스키마에서 url 필드를 제거해 모델이 URL 을 출력할 자리 자체를 없앴다. URL 은 검색 그라운딩이 반환한 실제 소스 URI 만 후보가 되고, probe_url() 의 3중 검사 — HTTP 200 · soft-404 마커 탐지 · 항목명 토큰 본문 대조 — 를 통과해야만 부착된다. SSRF 방지를 위해 사설 IP 로 해석되는 호스트는 프로브하지 않는다. 모델이 규칙을 어기고 URL 을 넣는 경우에 대비해 scrub_model_urls() 가 파이프라인 진입 직후와 직렬화 직전 두 번 훑는다.

해소: C-4 · C-5 — H-1 직접 차단

F-3

그라운딩 강제

검증 호출은 extract_grounding() 으로 응답의 grounding_chunks 를 파싱해 실제로 검색이 일어났는지 확인한다. 그라운딩이 없으면 그 배치 전체가 미검증으로 처리된다. 통과한 경우에도 grounding_mentions() 가 항목명 토큰이 검색 결과 제목·스니펫·URI 에 실제로 등장하는지 코드가 직접 대조한다. 모델의 "verified": true 는 그 자체로 아무 효력이 없다.

해소: C-3 — H-1 · H-3 공통 원인

F-4

반증형 이중 검증

검증 프롬프트를 "존재를 확인하라"에서 "실재하지 않는다는 증거를 찾아라"로 뒤집고, 추천 이유 등 생성 맥락은 일절 넘기지 않는다. 온도가 다른 2회 호출 (0.0 / 0.4)이 모두 통과해야 인정한다. 환각은 재현성이 낮으므로 이중 통과 요구가 비용 대비 효과가 가장 큰 필터다.

해소: C-2

F-5

자격증 레지스트리 + 등급 문법

국가기술자격·국가전문자격·주요 공인 민간/국제 자격 목록과 각 자격의 유효 등급 집합을 코드가 보유한다. check_certification_name() 이 명칭에서 등급을 분리해, 등급 체계가 없는 자격증에 급수가 붙었거나 존재하지 않는 등급이면 네트워크 호출 없이 즉시 제외한다. 검색으로는 잡히지 않던 유형이다 — 빅데이터분석기사 2급 을 검색하면 상위 결과에 원본 자격증이 잡히기 때문에 LLM 검증이 가장 잘 속는 지점이었다. 레지스트리 미등재 항목은 자동 통과가 아니라 F-3·F-4 검증 대상이 된다.

해소: H-3 의 주 유형 — 결정론적 차단

F-6

STAR 근거 결속

생성 전에 assess_star_readiness() 가 입력을 경험 블록으로 쪼개고 5개 신호(분량·행동동사·수치 성과·기간·역할)로 채점한다. 4개 미만이면 LLM 에 STAR 생성을 요청하지 않고 스키마에서 필드 자체를 제거한 뒤, 무엇을 더 적어야 하는지 코칭을 반환한다.

생성한 경우에도 각 슬롯에 <슬롯>_source_quote 를 강제하고, validate_star_entries() 가 ① 인용문이 원문에 실제로 존재하는지 대조하고 ② 원문에 없는 수치를 쓴 슬롯을 삭제하며 ③ 슬롯 간 인용 중복도가 60% 를 넘으면 '단순 재구조화'로 판정해 품질 경고를 붙인다. Action·Result 가 근거를 잃으면 그 경험은 통째로 폐기된다.

해소: C-8 · C-9 — H-2 의 두 얼굴(재구조화·창작)을 각각 차단

F-7

fail-closed 일관화 · 정규화 매칭

누락 필드의 기본값을 전부 '불합격'으로 통일했다. upcoming 을 실제로 검사하고, 마감일 파싱 실패는 무효 처리한다. 검증 결과 매핑은 norm_name() 으로 공백·괄호·구두점을 제거한 키를 쓴다. 크롤링 실패 시 "추론하라"는 지시문은 "추론을 금지하고 데이터 부재를 보고하라"로 교체했다. 채용공고는 본 분석에서 생성하지 않고 검색 그라운딩 단계에서만 만들어진다.

해소: C-6 · C-7 · C-10 · C-11

F-8

감사 추적

VerificationAudit 이 모든 통과·제거·강등을 사유와 함께 기록하고, 결과 JSON 의 verification_audit 과 rejected_by_guard 로 노출한다. 이제 "환각이 몇 건 걸러졌고 추천이 왜 비었는지"를 산출물만 보고 답할 수 있다.

07 — 결과와 트레이드오프

무엇이 좋아지고 무엇을 내주었나

환각은 이제 프롬프트 준수가 아니라 코드 통과 여부로 결정된다. 모델이 규칙을 어겨도 산출물에는 반영되지 않는다 — 근거 없는 URL 은 제거되고, 원문에 없는 수치는 삭제되며, 없는 등급이 붙은 자격증은 네트워크 호출 전에 걸러진다.

대가는 추천 개수의 감소다. 검증을 통과하는 항목만 남으므로 결과가 비는 경우가 늘어난다. 이것은 결함이 아니라 의도된 교환이며, 그래서 빈 결과에는 항상 이유와 사용자가 직접 확인할 검색어가 따라붙는다. 지어낸 3개보다 검증된 1개가, 검증된 1개보다 "확인되지 않았다"는 정직한 0개가 낫다는 것이 v3.0 의 입장이다.

비용 측면에서는 반증형 이중 검증과 URL 프로브로 카테고리당 호출·왕복이 늘었다. _DUAL_PASS_VERIFY 와 _MAX_URL_PROBES 로 조절할 수 있게 두었다.

남은 과제. ① 자격증 레지스트리는 수동 관리 목록이므로 Q-Net 등 공식 등록 API 와 동기화하는 편이 안전하다. ② 동아리·학회는 공개 웹 정보가 희소해 검증 통과율이 구조적으로 낮다 — 학교별 공식 동아리 목록을 사전 수집하는 방향이 근본 해법이다. ③ 실사용 로그에서 verification_audit 의 드롭 사유 분포를 모니터링해 어떤 게이트가 실제로 일하고 있는지 확인해야 한다.
